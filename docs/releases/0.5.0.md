# StoryMap 0.5.0

Prepared 2026-09-30. Adds the generic `GeoMap` layer, the legacy `leaflet` fenced-block
dialect in both hosts, and a versioned Obsidian settings structure. The private workspace
root, site and example package versions are independent.

This is a **minor** release. It is **purely additive**: `story-map-core/src/types.ts` gained
210 lines and removed none, and no public export was removed or renamed. Existing
`storymap/v1` documents and hand-written `StoryMapConfig` literals compile and behave
unchanged. See [Upgrade notes](#upgrade-notes).

## Highlights

- **A generic `GeoMap` layer under `StoryMap`.** `react-story-map` exports `<GeoMap />`,
  which owns the Leaflet lifecycle, tile sources, generic markers, `mapzoom` zoom visibility,
  tooltips, and note links. `StoryMap` now composes it as a layer above it
  (`MapCanvas.tsx`) instead of owning Leaflet directly, and its DOM is unchanged. A
  storyless map is therefore a first-class rendering, not a Story with the slides removed.
- **A second fenced-block dialect: ` ```leaflet `.** Legacy Obsidian Leaflet blocks now
  render in both hosts. They are parsed by a dedicated parser in
  `story-map-core/src/leaflet.ts` and **never** enter the `storymap/v1` Zod schema; a
  storyless map is never encoded as fake Story slides. The dialect keeps its historical key
  spelling (`lat`, `long`, `defaultZoom`, `markerFolder`, `mapmarker`) so existing content
  renders without edits.
- **One Leaflet runtime per page.** The Remark client reads an explicit
  `data-story-map-kind="story" | "map"` discriminator and mounts the matching renderer from
  a single module. A page holding a story and a map loads Leaflet and
  `leaflet/dist/leaflet.css` exactly once.
- **Nothing is silently ignored.** A recognized-but-unimplemented `leaflet` key produces a
  `GeoMapDiagnostic` naming that key, rendered under the map. An unrecognized key is
  reported separately as `leaflet-unknown-key`, so a typo is not confused with a scheduled
  feature. The per-key record lives in [the compatibility matrix](../leaflet-compatibility.md).
- **Cross-host parity is asserted, not assumed.** `remark-story-map/src/parity.test.ts` runs
  the four production blocks through both the Obsidian and Remark adapters and asserts
  identical marker selection, order, tile source and diagnostics.

## Upgrade notes

Existing `story-map` YAML documents need no edits, and the source schema identifier is still
`storymap/v1`. No public type gained a required field, so a hand-written `StoryMapConfig`
literal keeps compiling and keeps its meaning. Unlike `0.3.0` and `0.4.0`, there is no
`TS2741` to fix here.

The one behavioral change to an existing surface is a bug fix. A marker tooltip holding a
note link is now bound interactive and held open while the pointer travels to it, based on
the note link itself rather than on whether the host supplies callbacks. Hosts with
callbacks (Obsidian) already took that path and are unaffected. A host whose marker link is
a plain `href` (Docusaurus) previously got an anchor that rendered with a correct `href` and
could not be clicked; that is fixed. See [the compatibility matrix](../leaflet-compatibility.md#the-marker-note-link-was-unreachable-and-the-fix-was-not-where-it-looked).

### Consuming the `leaflet` dialect on Docusaurus

The plugin handles both dialects. A host that previously carried a separate
`remark-obsidian-leaflet` plugin plus its own CDN bootstrap can delete both:

```js
import remarkStoryMap from '@story-map/remark-story-map';

const storyMapOptions = {
  vaultRoot: '/path/to/vault',
  resolveNoteHref,            // the host's existing published-route authority
  leafletDefaults: { theme: 'auto' },
};
```

Published routes stay the host's decision through `resolveNoteHref`; nothing in this package
implements slug or permalink policy. A host whose theme toggle is not
`prefers-color-scheme` must bridge `map.theme: auto` in its own stylesheet and must declare
**both** directions — a dark-only bridge is outranked by the renderer's own
`prefers-color-scheme` block on a dark OS. `examples/docusaurus/story-map-theme.css` is a
working bridge.

### New in `@story-map/story-map-core`

`GeoMapConfig`, `GeoMapOptions`, `GeoMapControlOptions`, `GeoMapDiagnostic`, `GeoMarker`,
`MarkerTypeDefinition`, `MarkerTypeIcon`, `MarkerTooltipDisplay`, `MarkerZoomRange`,
`TileSource`, `TileSourceInput`, `TileSources`, `LatLngTuple`, the `parseLeafletSourceYaml`
parser, marker-type and tile helpers, `DEFAULT_TILE_URL` and `DEFAULT_TILE_ATTRIBUTION`.

The built-in tile source is `https://tile.openstreetmap.org/{z}/{x}/{y}.png` with visible
attribution `© OpenStreetMap contributors`. CARTO Basemaps is **not** the default because it
now requires an API key. A theme is presentation and never replaces a configured
`tileUrl`; a configured dark tile source is stored but not yet requested.

### New in `@story-map/react-story-map`

`<GeoMap />` with `GeoMapProps`, `GeoMapRuntime` and `GeoMapFocusContext`. A standalone
`<GeoMap>` renders the same themed `.story-map` root as `StoryMap`, so all six built-in
themes and the `--story-map-*` variables style a plain map with no duplicated CSS.

### Obsidian plugin

Settings migrate to a versioned `version: 2` structure with `story`, `map`, `markers`,
`interaction` and `leafletCompatibility` sections, without losing existing defaults. Default
resolution is structurally separated per dialect, so a Leaflet-only default center, marker
registry, tooltip default or unit system is unreachable from a native story map. An optional
"Import settings from Obsidian Leaflet" command reads the community plugin's data from its
published id `obsidian-leaflet-plugin` first, then the un-suffixed directory.

## Known limitations

- **A configured dark tile source is never requested.** The renderer always uses the light
  source and lets the theme's tile filter darken it. `darkMode` is parsed and reported, not
  acted on.
- **`P1` controls are deliberately inert.** `noUI`, `noScrollZoom`, `recenter`, `lock` and
  `zoomDelta` parse and carry, and report a `leaflet-pending-p1` diagnostic. Implementing
  them would make that diagnostic a lie, so they are left pending rather than faked.
- **`P2` file layers and `P3` image maps, measurement and drawing** are parsed and diagnosed
  but do not render. They are scheduled, not implemented.
- **Shift-click coordinate copy** resolves the nearest marker by map projection within a
  16 px radius rather than binding a handler per marker layer, because Leaflet does not
  expose the originating layer on a propagated click.
- **On Docusaurus, any page holding a story or map host logs React error #418.** This is
  pre-existing on the already-deployed story-map path and not introduced here; it reproduces
  on `0.1.1` with no `leaflet` block on the page. The client mounts a second `createRoot`
  into a host element Docusaurus's own React tree already owns. It is recoverable and the
  page renders correctly. Fixing it means changing host ownership, which is a
  Docusaurus-integration change rather than a compatibility one.
- Map tiles and remote example media require access to their external providers.
- Production site/example builds still report large JavaScript chunk warnings.

## Release artifacts and tags

| Target | Version/tag | Artifacts |
| --- | --- | --- |
| Obsidian | `0.5.0` | `main.js`, `manifest.json`, `styles.css` |
| npm libraries | `npm-v0.5.0` | Core, React and Remark packages, each `0.5.0` |

Both tags point to the same release commit. Obsidian artifacts are built under
`packages/obsidian-story-map/dist/`, with dependency notices embedded in `main.js`. The root
`versions.json` maps `0.5.0` to `1.8.7`. The plugin remains desktop-only and requires
Obsidian **1.8.7 or newer**.

`0.5.0` is a new number rather than a re-publish of `0.4.0`: an older, unrelated `0.4.0` is
already on npm and does not contain the `leaflet` dialect, and published versions are
immutable. `release-npm.mjs` refuses to overwrite a version whose registry integrity differs,
which is exactly the guard that made the collision visible instead of silent.

Obsidian verification was run against a real sandbox vault, not only in unit tests: the
nine-item manual pass, including the inline `leaflet` block, recursive `markerFolder`, the
settings importer, and Page-preview note links. Two defects were found and fixed during
that pass: a release-check stub missing `MarkdownRenderChild`, which would have failed every
Obsidian release, and an importer reading the wrong plugin directory.

Docusaurus verification was run against a real production build in a headless browser. All
32 `leaflet` blocks across 31 pages of `kywk.github.io` render through this release, and the
site's old `remark-obsidian-leaflet` plugin, CDN bootstrap and superseded CSS are deleted.
Measured marker counts matched the pre-migration survey exactly: Chile 28, Egypt 27, Kuala
Lumpur 5, Xinjiang 20, Zao 0. Both Egypt maps mounted from one runtime as `sm-1`/`sm-2`, an
SPA round trip returned exactly 2 hosts / 2 containers / 2 panes, and no absolute local path
reached the HTML.

Two further defects were found there and fixed, neither visible to the automated suite:

1. A marker note link rendered with a correct `href` and could not be clicked, because
   `tooltipBinding` derived interactivity from host callbacks rather than from the note
   link. The previous test asserted the broken behavior as correct.
2. The Docusaurus `auto` theme bridge was one-directional, so a dark-OS reader who switched
   the site to light still got a dark map.

The site is **not yet deployed** at the time of writing: it still resolves these packages
from local tarballs, because the publish step had not run. The recorded evidence is
[here](../acceptance/2026-09-30-docusaurus-leaflet-migration.md).

Not run for 0.5.0: a clean-machine community-directory install of the plugin, and a
fresh native Obsidian lifecycle pass on a clean machine.
